= Specifications

== Requirements

This document records the current behavior of Mill's Git-based version
calculation and the cases that expose the fork-versioning problem.

The implementation under characterization is `mill.util.VcsVersion`
(`libs/util/src/mill/util/VcsVersion.scala`) and its use by
`millVersion` / `millLastTag` in `build.mill`.

=== Current behavior (characterization)

These requirements describe the existing implementation. They are not
statements of the desired corrected behavior.

* CV-01 — Exact tag at HEAD
+
When HEAD is exactly tagged, `git describe --exact-match --tags --always HEAD`
provides the tag. The calculated commit count is zero.
+
link:https://github.com/vayshya/mill/blob/fork-versioning/libs/util/test/src/mill/util/VcsVersionGitTests.scala[CV-01 test]

* CV-02 — HEAD after a reachable tag
+
When HEAD is not exactly tagged, the implementation selects a tag using
`git describe --abbrev=0 --tags`. It then counts commits reachable from HEAD
but not reachable from that tag using `git rev-list HEAD --not <tag> --count`.
+
link:https://github.com/vayshya/mill/blob/fork-versioning/libs/util/test/src/mill/util/VcsVersionGitTests.scala[CV-02 test]

* CV-03 — No reachable tags
+
When no tag can be described, `lastTag` is empty and the commit count is the
number of commits reachable from HEAD.
+
link:https://github.com/vayshya/mill/blob/fork-versioning/libs/util/test/src/mill/util/VcsVersionGitTests.scala[CV-03 test]

* CV-04 — Tag selection
+
Tag selection is delegated to Git's `git describe` behavior. It is not based
on commit timestamps or on a separately computed upstream release baseline.
+
link:https://github.com/vayshya/mill/blob/fork-versioning/libs/util/test/src/mill/util/VcsVersionGitTests.scala[CV-04 test]

* CV-05 — Dirty working tree
+
The dirty hash is derived from the textual output of `git diff HEAD`.
An empty diff produces no dirty hash.
+
link:https://github.com/vayshya/mill/blob/fork-versioning/libs/util/test/src/mill/util/VcsVersionGitTests.scala[CV-05 test]

* CV-06 — No Git repository
+
If resolving HEAD fails because the directory is not a Git repository, the
returned state has revision `no-vcs`, no tag, zero commits, no dirty hash,
and no VCS marker.
+
link:https://github.com/vayshya/mill/blob/fork-versioning/libs/util/test/src/mill/util/VcsVersionGitTests.scala[CV-06 test]

* CV-07 — Mill version fallback
+
The `VcsVersion.formatMillVersion` policy used by the top-level
`millVersion` task returns `SNAPSHOT` when the calculated state has no tag.
This fallback is separate from `VcsVersion.State.format`, which can format
an untagged state. The unit test exercises the formatting policy directly,
not the build task itself.
+
link:https://github.com/vayshya/mill/blob/fork-versioning/libs/util/test/src/mill/util/VcsVersionTests.scala[CV-07 test]

* CV-08 — CI dirty-state handling
+
When the `millVersion` formatting policy is given `isCi = true`, it clears
`dirtyHash` before formatting. Outside CI, the dirty hash is retained.
The unit test exercises this policy directly, not environment detection in
the build task.
+
link:https://github.com/vayshya/mill/blob/fork-versioning/libs/util/test/src/mill/util/VcsVersionTests.scala[CV-08 test]

=== Reproduction scenarios

The following scenarios characterize the current implementation and make
the upstream-versus-fork counting issue observable. The synthetic Git
histories must be created in temporary local repositories; tests must not
depend on network access or the live Mill repository.

* CV-09 — Commits on the fork branch after the release tag include the upstream baseline
+
Create a linear history:
+
[source,text]
----
A --- B --- C --- D --- E --- F --- G
          tag                  HEAD
----
+
Let C carry tag `1.4.0-M2`. The `upstream` branch advances through D and E;
the `fork` branch then starts at E and adds F and G. With no other tags,
the current implementation reports `lastTag = Some("1.4.0-M2")` and
`commitsSinceLastTag = 4`, counting both upstream and fork commits.
+
link:https://github.com/vayshya/mill/blob/fork-versioning/libs/util/test/src/mill/util/VcsVersionGitTests.scala[CV-09 test]

* CV-10 — Fork checkout without available tags
+
Create a repository with seven commits and no tags in the repository or on
its remote. The checkout has no reachable tags, so the VCS state has no last
tag and counts all seven commits. The `millVersion` formatting policy
returns `SNAPSHOT`.
+
link:https://github.com/vayshya/mill/blob/fork-versioning/libs/util/test/src/mill/util/VcsVersionGitTests.scala[CV-10 test]



=== Regression requirements (desired behavior)

These requirements describe the intended fork-versioning behavior. They are
deliberately separate from the characterization cases above and are expected
to fail until the implementation supports an explicit upstream baseline.

* CV-12 — Exclude upstream commits after rebasing the fork
+
Create a fork branch from release-tagged commit C and add fork commits F and
G. Advance the original `upstream` branch from C with commits D and E, then
rebase the fork branch onto E. The resulting fork HEAD is a descendant of E;
the `upstream` ref remains at E. The calculated release tag remains
`1.4.0-M2`, and only the two rebased fork commits count:
`commitsSinceLastTag = 2`. The test must use an actual `git rebase`.
+
link:https://github.com/vayshya/mill/blob/fork-versioning/libs/util/test/src/mill/util/VcsVersionGitTests.scala[CV-12 test]

* CV-13 — Use an upstream release tag when the checkout has no local tags
+
Create a local bare upstream repository containing release tag
`1.4.0-M2` and commits after it. Clone it with `--no-tags`, configure the
remote as `upstream`, and add two fork-only commits. The checkout must have
no local tags while the upstream remote still advertises the release tag.
The calculated state must use `1.4.0-M2` and count only the two fork-only
commits.
+
link:https://github.com/vayshya/mill/blob/fork-versioning/libs/util/test/src/mill/util/VcsVersionGitTests.scala[CV-13 test]

=== Supported branch workflow

Merge-based integration is not supported by the fork-versioning model.
All development branches and forks must be rebased onto their original
(upstream) branches; changes from an original branch must be incorporated
with `git rebase`, not by merging that branch into the fork.

The versioning requirements and regression tests assume that the fork is
based on the latest applicable commit of its original branch, followed only
by the fork's own commits.

=== Scope and constraints

* These tests characterize the current behavior; they must not silently
  encode the proposed corrected versioning algorithm as current behavior.
* Regression requirements for the corrected algorithm must be specified
  separately after the current behavior is captured.
* Tests should use temporary repositories and local refs only.
* Do not run GitHub Actions or CI as part of adding this specification.
