= Specifications

== Requirements

This document records the current behavior of Mill's Git-based version
calculation and the cases that expose the fork-versioning problem.

The implementation under characterization is `mill.util.VcsVersion`
(`libs/util/src/mill/util/VcsVersion.scala`) and its use by
`millVersion` / `millLastTag` in `build.mill`.

=== Current behavior (characterization)

These requirements describe the existing implementation. They are not
statements of the desired corrected behavior.

* CV-01 — Exact tag at HEAD
+
When HEAD is exactly tagged, `git describe --exact-match --tags --always HEAD`
provides the tag. The calculated commit count is zero.
+
link:https://github.com/vayshya/mill/blob/fork-versioning/libs/util/test/src/mill/util/VcsVersionGitTests.scala[CV-01 test]

* CV-02 — HEAD after a reachable tag
+
When HEAD is not exactly tagged, the implementation selects a tag using
`git describe --abbrev=0 --tags`. It then counts commits reachable from HEAD
but not reachable from that tag using `git rev-list HEAD --not <tag> --count`.
+
link:https://github.com/vayshya/mill/blob/fork-versioning/libs/util/test/src/mill/util/VcsVersionGitTests.scala[CV-02 test]

* CV-03 — No reachable tags
+
When no tag can be described, `lastTag` is empty and the commit count is the
number of commits reachable from HEAD.
+
link:https://github.com/vayshya/mill/blob/fork-versioning/libs/util/test/src/mill/util/VcsVersionGitTests.scala[CV-03 test]

* CV-04 — Tag selection
+
Tag selection is delegated to Git's `git describe` behavior. It is not based
on commit timestamps or on a separately computed upstream release baseline.
+
link:https://github.com/vayshya/mill/blob/fork-versioning/libs/util/test/src/mill/util/VcsVersionGitTests.scala[CV-04 test]

* CV-05 — Dirty working tree
+
The dirty hash is derived from the textual output of `git diff HEAD`.
An empty diff produces no dirty hash.
+
link:https://github.com/vayshya/mill/blob/fork-versioning/libs/util/test/src/mill/util/VcsVersionGitTests.scala[CV-05 test]

* CV-06 — No Git repository
+
If resolving HEAD fails because the directory is not a Git repository, the
returned state has revision `no-vcs`, no tag, zero commits, no dirty hash,
and no VCS marker.
+
link:https://github.com/vayshya/mill/blob/fork-versioning/libs/util/test/src/mill/util/VcsVersionGitTests.scala[CV-06 test]

* CV-07 — Mill version fallback
+
The top-level `millVersion` task returns `SNAPSHOT` when the calculated
state has no tag. This fallback is implemented in `build.mill`, not in the
`VcsVersion` API. It is not covered by the `VcsVersion` unit tests.

* CV-08 — CI dirty-state handling
+
The top-level `millVersion` task clears `dirtyHash` when the `CI`
environment variable is present; outside CI, the dirty hash is retained.
This policy is implemented in `build.mill`, not in the `VcsVersion` API,
and is not covered by the `VcsVersion` unit tests.

=== Upstream and tag discovery approaches to characterize

This section records alternative discovery approaches for investigation. It
does not select or prescribe an implementation. Their behavior and
applicability must be characterized before any desired algorithm is specified.

==== Discovering the original upstream reference

Potential sources for identifying the original branch or its remote include:

* The current branch's Git configuration:
  `branch.<name>.remote` and `branch.<name>.merge`, which can identify its
  configured remote and upstream branch.
* The remote-tracking default branch, such as
  `refs/remotes/<remote>/HEAD`, which may identify a remote's default branch
  but does not necessarily identify the original branch from which a fork
  was created.
* An explicitly configured remote and branch, supplied by the build or
  repository configuration.
* Conventional remote names such as `upstream` or `origin`. These are
  naming conventions only and cannot by themselves establish which remote
  is the original repository.

The characterization should establish what information is available in a
normal checkout, in a fork checkout, and in a checkout with multiple remotes
or no configured upstream.

==== Discovering the common upstream commit

Potential ways to locate a common commit between the current HEAD and a
candidate upstream reference include:

* `git merge-base HEAD <upstream-ref>`, which finds a best common ancestor.
* `git merge-base --all HEAD <upstream-ref>`, which exposes all best common
  ancestors if the history has more than one.
* Commit-graph inspection with commands such as
  `git rev-list` or `git log`, to enumerate and compare the commits
  reachable from the two references.

The characterization should establish how these methods behave for a
rebased fork, when the upstream has advanced, and when there are multiple
candidate upstream references. Merge-based histories are outside the
supported branch workflow described below.

==== Discovering release tags applicable to a commit

Potential ways to find release tags relevant to a candidate common commit
include:

* `git describe --abbrev=0 <commit>`, which asks Git for the nearest
  reachable tag according to `git describe` semantics.
* `git tag --merged <commit>` or
  `git for-each-ref --merged=<commit> refs/tags`, which enumerate tags
  whose commits are ancestors of the specified commit.
* Inspecting tag refs and their target commits directly, then comparing
  their ancestry relationship to the candidate common commit.
* Inspecting tags advertised by a remote with
  `git ls-remote --tags <remote>`. This reports remote tag references; it
  does not by itself make the tagged objects available in the local object
  database.

The characterization should distinguish locally available tags from tags
advertised by a remote, annotated tags from lightweight tags, and tags that
are ancestors of the candidate common commit from tags that are not.

=== Reproduction scenarios

The following scenarios characterize the current implementation and make
the upstream-versus-fork counting issue observable. The synthetic Git
histories must be created in temporary local repositories; tests must not
depend on network access or the live Mill repository.

* CV-09 — Commits on the fork branch after the release tag include the upstream baseline
+
Create a linear history:
+
[source,text]
----
A --- B --- C --- D --- E --- F --- G
          tag                  HEAD
----
+
Let C carry tag `1.4.0-M2`. The `upstream` branch advances through D and E;
the `fork` branch then starts at E and adds F and G. With no other tags,
the current implementation reports `lastTag = Some("1.4.0-M2")` and
`commitsSinceLastTag = 4`, counting both upstream and fork commits.
+
link:https://github.com/vayshya/mill/blob/fork-versioning/libs/util/test/src/mill/util/VcsVersionGitTests.scala[CV-09 test]

* CV-10 — Fork checkout without available tags
+
Create a repository with seven commits and no tags in the repository or on
its remote. The checkout has no reachable tags, so the VCS state has no last
tag and counts all seven commits. The `millVersion` task's `SNAPSHOT`
fallback is a separate build-level behavior and is not asserted by this Git
state test.
+
link:https://github.com/vayshya/mill/blob/fork-versioning/libs/util/test/src/mill/util/VcsVersionGitTests.scala[CV-10 test]



* CV-11 — CI checkout fetches history without tags

The `test-dist` job in GitHub Actions Run #190 checks out the repository
with `fetch-depth: 0` and `fetch-tags: false`. A full commit history does
not make tag refs available when tag fetching is disabled. In this checkout,
`VcsVersion` cannot discover a local release tag, and the build-level
`millVersion` fallback therefore produces `SNAPSHOT`.

The `mill.scripts.ExampleListTests.exampleListUrls` test then fails its
assertion that the generated download URL does not contain `SNAPSHOT`.
The failure occurs while checking the generated URL; this run does not
attempt to download the Maven artifact and does not establish whether a
SNAPSHOT artifact exists in Maven Central.

Observed in
link:https://github.com/vayshya/mill/actions/runs/43934491530[GitHub Actions Run #190],
job `test-dist`.

=== Target requirements (desired behavior)

These requirements describe the intended fork-versioning behavior. They are
deliberately separate from the characterization cases above. They specify
the target behavior; they are not characterization requirements and are not
to be added to the characterization test suite.

* CV-12 — Exclude upstream commits after rebasing the fork
+
Create a fork branch from release-tagged commit C and add fork commits F and
G. Advance the original `upstream` branch from C with commits D and E, then
rebase the fork branch onto E. The resulting fork HEAD is a descendant of E;
the `upstream` ref remains at E. The calculated release tag remains
`1.4.0-M2`, and only the two rebased fork commits count:
`commitsSinceLastTag = 2`. The test must use an actual `git rebase`.
+
The characterization test for this scenario records the current behavior:
all four commits after the tag are counted. An acceptance test must verify
the target behavior specified above after the implementation is changed.

* CV-13 — Use an upstream release tag when the checkout has no local tags
+
Create a local bare upstream repository containing release tag
`1.4.0-M2` and commits after it. Clone it with `--no-tags`, configure the
remote as `upstream`, and add two fork-only commits. The checkout must have
no local tags while the upstream remote still advertises the release tag.
The calculated state must use `1.4.0-M2` and count only the two fork-only
commits.
+
The characterization test for this scenario records the current behavior:
the unfetched remote tag is not discovered, and all seven commits are
counted. An acceptance test must verify the target behavior specified above
after the implementation is changed.

=== Supported branch workflow

Merge-based integration is not supported by the fork-versioning model.
All development branches and forks must be rebased onto their original
(upstream) branches; changes from an original branch must be incorporated
with `git rebase`, not by merging that branch into the fork.

The target versioning requirements and their acceptance tests assume that
the fork is based on the latest applicable commit of its original branch,
followed only by the fork's own commits.
