= Local Repository Lifecycle Specifications

== Overview

The Local Repository Lifecycle feature defines how Mill manages the generated local artifact repository exposed as `dist.raw.localRepo` while the Mill daemon and Zinc workers are running.

The repository is a temporary, generated artifact store used by Mill. Its lifecycle must be compatible with operating systems that prevent deletion of files while a process still has them open, particularly Windows.

This feature is concerned with the complete lifecycle rather than repository selection.

The raw launcher resolves the long-lived Mill daemon's runner classpath through Coursier, using
the generated local repository as a file-based artifact source. Those local artifacts must be
copied into a stable Coursier cache before the daemon is launched. The daemon must never retain
a runner classpath that points directly into the temporary `dist.raw.localRepo` directory.
This is distinct from the Zinc worker classpath: both are lifecycle consumers, but the daemon
runner classpath is established before the first build task is evaluated.

. Mill resolves artifacts from the generated local repository.
. The daemon and Zinc workers finish using repository artifacts and release file handles.
. The clean operation physically removes the repository directory.
. Where supported by the launcher path, Mill recreates and repopulates the repository.
. The already-running daemon and workers remain usable throughout the lifecycle.

== Relationship to other features

* `mill-repositories` defines which artifact repositories Mill uses to resolve dependencies.
* `zinc-incremental-compilation` uses Zinc workers for incremental Scala compilation. Those workers are consumers of artifacts in the generated local repository and may outlive an individual Mill command. Their use of repository artifacts is therefore an important lifecycle scenario: they must not retain file handles that prevent cleanup, or observe files changing underneath an operation already in progress.
* `local-repository-lifecycle` defines how Mill's generated local repository is used, released, cleaned, deleted, and recreated, including safe behavior when consumers such as Zinc workers are still active.

These features are related but have different responsibilities. The Zinc feature provides a relevant consumer scenario; the local repository lifecycle feature owns the repository cleanup and concurrent-update guarantees. A repository configuration test must not be used as a substitute for lifecycle and file-handle regression coverage.

== Lifecycle guarantees

The requirements and their verification criteria are defined below.

The key guarantees are:

* Repository JARs are not left open by the daemon or Zinc workers after resolution has completed.
* Cleaning `dist.raw.localRepo` physically removes the directory without requiring the daemon or workers to terminate.
* The bootstrap-launcher path can recreate a populated repository after clean and continue using the existing daemon.
* Concurrent repository updates do not change the data observed by operations that are already using an earlier repository state.
* The raw-launcher regression checks handle release and physical deletion independently of the unrelated post-clean daemon SNAPSHOT resolution path.

== Verification

The cross-platform file-handle regression is implemented by link:test-local-repository-lock.ps1[the local repository lock test].

The test distinguishes bootstrap and raw launcher scenarios. The bootstrap scenario includes clean, rebuild, and daemon reuse. The raw-launcher scenario verifies file-handle release and physical deletion; its post-clean rebuild is deliberately excluded because that would also test a separate SNAPSHOT resolution path.


== Characterization

The following observations describe the implementation at the time these tests were added. They are intentionally separate from the target lifecycle guarantees below: a characterization test records the current behavior and must not be interpreted as approval of that behavior.

=== Characterization observations

The following numbered observations describe the implementation at the time these tests were added. The `LRL-CHAR` identifier series is reserved for characterization records; it is independent of the `LRL` target-requirement series below. These records document observed behavior and are not target guarantees.

==== LRL-CHAR-01 — Windows raw-daemon classpath uses Coursier-cache-mediated local artifacts

On the investigated Windows run, the raw daemon JVM command line contained runner artifacts resolved from `dist.raw.localRepo` through a path under the Coursier file cache. The encoded/cache path did not begin with the local repository directory, so checking only whether the resolved file path starts with the repository path misses its local-repository origin.

==== LRL-CHAR-02 — Windows raw-launcher version command fails while daemon remains running

On that Windows run, the raw launcher's initial `show millVersion` command returned exit code 1 even though the daemon process remained running and its command line exposed the Coursier-cache-mediated local repository artifacts. The characterization therefore inspects the daemon independently of the launcher command's exit code and uses the bootstrap launcher as a client for the subsequent compile and clean operations.

==== LRL-CHAR-03 — Linux raw daemon and Zinc workers expose local-repository artifacts on their classpaths

On the investigated Linux run, the raw daemon runtime classpath contained JARs from `dist.raw.localRepo`. Zinc workers were also observed with local-repository artifacts on their runtime classpaths.

==== LRL-CHAR-04 — Daemon and Zinc workers outlive individual client commands

The daemon and Zinc workers are long-lived across client commands. The characterization must keep both alive while checking the result of `clean`; shutting them down first would hide the lifecycle behavior.

==== LRL-CHAR-05 — Investigated clean outcome differs between Windows and Linux

On Windows, the investigated raw-launcher clean failed while a live process retained a repository artifact. On Linux, filesystem deletion succeeded even though the daemon/workers remained alive; this does not establish that those processes can resolve the deleted local SNAPSHOT again.

==== LRL-CHAR-06 — No macOS outcome has been established

The investigated macOS run did not complete, so no prior macOS outcome is claimed here. The characterization job records its result independently.

=== Characterization test

`characterize-local-repository-lifecycle.ps1` starts the daemon with the raw launcher, records daemon and Zinc worker command lines, then uses the bootstrap launcher as a client to compile and run `clean dist.raw.localRepo` while that same daemon and its workers remain alive. This keeps the raw-daemon classpath observation separate from the Windows raw-client exit-code anomaly. It expects the currently observed Windows-versus-POSIX deletion behavior and reports whether daemon/worker command lines expose direct or Coursier-cache-mediated local repository paths.

These assertions are characterization only. When implementation behavior changes, update this section and the characterization expectations deliberately; do not weaken or repurpose the target requirements to make the characterization pass.

== Requirements

=== LRL-TAR-01 — Repository files must not remain locked after resolution

After Mill has resolved artifacts from the local repository, its daemon and Zinc worker processes must not retain open file handles to repository JARs that prevent the repository from being removed on Windows.

Verification:
* Run the local repository task through the launcher under test.
* Inspect the daemon JVM's runner classpath and verify that it contains no paths below `dist.raw.localRepo`.
* Inspect open file handles for files below `dist.raw.localRepo`.
* Verify that no repository files remain open.

=== LRL-TAR-02 — Clean must physically remove the local repository

The clean operation for `dist.raw.localRepo` must remove the repository directory and its contents from disk, even while the Mill daemon and its workers remain running, provided they no longer hold files in that directory open.

Verification:
* Start the daemon and workers by invoking `dist.raw.localRepo`.
* Record the daemon and worker process IDs.
* Run clean.
* Verify that the repository directory no longer exists.
* Verify that the original daemon and worker processes are still alive.

=== LRL-TAR-03 — Bootstrap launcher must rebuild the repository after clean

After a successful clean, the bootstrap launcher must be able to recreate `dist.raw.localRepo` with its expected artifacts. Reusing the daemon after the rebuild must not require terminating the previously running daemon or workers.

Verification:
* Clean the repository using the bootstrap launcher scenario.
* Invoke `dist.raw.localRepo` again.
* Verify that the directory is recreated and contains files.
* Verify that no repository files remain open and that the original daemon and worker processes are still alive.

=== LRL-TAR-04 — Raw launcher clean scenario must be isolated from rebuild resolution

The raw-launcher regression scenario verifies repository file-handle release and physical deletion. It must not treat a subsequent raw-launcher rebuild as part of this regression, because after deletion that rebuild can exercise the separate daemon SNAPSHOT dependency-resolution path.

Verification:
* Run the raw launcher scenario.
* Verify that repository files are not held open and that clean physically removes the repository.
* Do not assert raw-launcher rebuild behavior in this test.

=== LRL-TAR-05 — Repository must be created and populated when requested

When Mill resolves `dist.raw.localRepo`, the generated repository must be created if it does not exist and populated with the artifacts required by the requested operation. A successful task result must not leave the repository missing or unusable.

Verification:
* Start from a state where `dist.raw.localRepo` does not exist.
* Invoke `dist.raw.localRepo` through the supported launcher scenario.
* Verify that the repository directory is created and contains the expected artifacts.
* Invoke the task again and verify that it succeeds while reusing the existing daemon.

The cross-platform lifecycle regression script is the integration-test location for this scenario; its initial-resolution checks must assert repository existence and contents, not only successful task exit.

=== LRL-TAR-06 — Lock diagnostics must identify processes holding repository files

When the lifecycle regression detects an open file under `dist.raw.localRepo`, its diagnostic output must identify the affected file and the process or processes holding it open. Where the operating system exposes the information, diagnostics must include process identifiers and useful process details (such as executable name and command line). Failure to collect supplemental process details must not hide the original lock failure.

Verification:
* Cause or retain an open handle to a file under `dist.raw.localRepo`.
* Run the lock-detection check.
* Verify that the failure output identifies the file and locking process identifiers.
* Verify that available process details are included and that unavailable supplemental details are reported without suppressing the lock failure.

The cross-platform file-handle regression script already contains platform-specific lock probes and process-detail formatting; the assertions and failure output must continue to satisfy this requirement.

=== LRL-TAR-07 — Concurrent repository updates must preserve the state observed by active consumers

An operation that has started using the generated local repository must continue to observe a consistent repository state for the duration of that operation, even if another process or operation updates the repository concurrently.

Publishing an updated repository state must not modify or remove files that are still needed by consumers of the previous state. A consumer must not observe a mixture of artifacts from the previous and updated states. The updated state must become visible as a complete state, rather than exposing a partially populated repository.

The implementation may use immutable repository generations, atomic publication, or another mechanism, but it must provide these isolation guarantees. An earlier repository state may be physically removed only after no active consumer can still depend on it.

Verification:
* Prepare an initial repository state containing identifiable artifact versions.
* Start a consumer that begins using the initial state and keep that operation active.
* Concurrently publish an updated state containing distinguishable artifact versions.
* Verify that the active consumer continues to observe the complete initial state and does not observe updated or mixed contents.
* Start a new consumer after publication and verify that it observes the complete updated state.
* Verify that files belonging to the initial state are not removed while the original consumer still depends on them, and can be reclaimed after that consumer finishes.

=== LRL-TAR-08 — Raw daemon runtime classpath must not depend on the deletable local repository

The raw launcher must not start its long-lived Mill daemon with runtime classpath entries located inside `dist.raw.localRepo`. The daemon outlives the launcher invocation, so any runner artifact loaded directly from that generated repository can remain open and prevent the repository from being cleaned on Windows. Local SNAPSHOT artifacts must be resolved into a stable location outside the generated repository before they are placed on the daemon runtime classpath. Re-resolution on a later daemon start must still observe a newly published local SNAPSHOT.

Verification:
* Build the raw launcher, then shut down the daemon and workers used to build it.
* Start a fresh daemon through the raw launcher with a command that does not evaluate `dist.raw.localRepo`.
* Inspect the daemon JVM command line and verify that its runtime classpath does not contain a path below `dist.raw.localRepo`.
* Verify that the same daemon can then evaluate `dist.raw.localRepo` and clean it while remaining alive.
* Republish a distinguishable local SNAPSHOT, start a new daemon, and verify that the new daemon resolves the updated artifact while the previous daemon's classpath remains stable.
