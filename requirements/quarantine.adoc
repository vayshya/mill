= Quarantine System Requirements
:toc:
:toclevels: 3
:sectnums:

== Purpose

Define the observable behavior of quarantined tests in Mill, including declaration, execution, diagnostics, test reports, and CI reporting.

A quarantined test is a test whose failure is expected to be temporarily tolerated. Its failure must remain visible and attributable, but must not fail the test task. A quarantine declaration is not a way to hide a test result.

== Scope

The current implementation is in the Java test module and provides the generated annotation `mill.javalib.api.Quarantined`. The requirements below describe the intended quarantine-system behavior. Where a requirement is not covered by an existing test, its acceptance-test ID is a test to add; it is not a claim that the behavior is already implemented.

Cross-language availability is a system requirement: languages with Mill test-module integrations must expose the same annotation name and semantics where technically applicable. The acceptance tests listed here currently target the Java integration unless a language-specific test is named.

== Terms

[cols="1,3",options="header"]
|===
|Term |Definition

|Quarantined test
|A test method explicitly marked with the quarantine annotation.

|Quarantine reason
|A non-empty explanation supplied at the declaration site for why the test is quarantined.

|Quarantined failure
|A test result with status `Failure` or `Error` and a valid quarantine declaration.

|Ordinary failure
|A test result with status `Failure` or `Error` and no valid quarantine declaration.

|Quarantine report
|The test output and CI summary that identify quarantined failures separately from ordinary failures.
|===

== Requirements

=== Declaration

==== QSYS-DECL-001 — Common annotation name

The quarantine declaration MUST use the same fully qualified annotation name across supported JVM languages: `mill.javalib.api.Quarantined`.

.Acceptance tests
* AT-QSYS-DECL-001a — Java test compilation and runtime discovery recognize `mill.javalib.api.Quarantined`.
* AT-QSYS-DECL-001b — Each additional supported JVM-language integration uses that exact fully qualified name and is recognized by the common test-result pipeline.

==== QSYS-DECL-002 — Mandatory reason

Every quarantine declaration MUST provide a reason. A declaration without a reason MUST fail compilation or validation before the test is run. An empty or whitespace-only reason MUST be rejected.

.Acceptance tests
* AT-QSYS-DECL-002a — A declaration with a non-empty reason compiles and is associated with the matching test result.
* AT-QSYS-DECL-002b — A declaration without a reason is rejected.
* AT-QSYS-DECL-002c — Empty and whitespace-only reasons are rejected.

==== QSYS-DECL-003 — Method-level association

A quarantine declaration MUST apply only to the test method on which it is declared. It MUST NOT accidentally classify another overload, parameterized invocation, method with a similar name, or another test in the same class as quarantined.

.Acceptance tests
* AT-QSYS-DECL-003a — Only the annotated JUnit 5 test method receives its quarantine reason.
* AT-QSYS-DECL-003b — An overloaded method without the annotation remains an ordinary test.
* AT-QSYS-DECL-003c — Every invocation of an annotated parameterized test is associated with the declaration and reason.

=== Execution and task outcome

==== QSYS-EXEC-001 — Quarantined failure does not fail the test task

A quarantined test result with status `Failure` or `Error` MUST be reported as a quarantined failure and MUST NOT, by itself, cause the Mill test task to fail.

.Acceptance tests
* AT-QSYS-EXEC-001a — A test suite containing only a failing quarantined test completes successfully at the Mill task level.
* AT-QSYS-EXEC-001b — A test suite containing both passing tests and failing quarantined tests completes successfully at the Mill task level.

==== QSYS-EXEC-002 — Ordinary failures remain fatal

An ordinary test result with status `Failure` or `Error` MUST fail the Mill test task, regardless of whether other tests in the same run are quarantined.

.Acceptance tests
* AT-QSYS-EXEC-002a — An ordinary assertion failure makes the test task fail.
* AT-QSYS-EXEC-002b — A run containing both an ordinary failure and a quarantined failure fails because of the ordinary failure.
* AT-QSYS-EXEC-002c — An ordinary error (not an assertion failure) makes the test task fail.

==== QSYS-EXEC-003 — Quarantine does not change successful results

A passing quarantined test MUST remain a passing test. Its quarantine declaration MUST NOT turn a successful result into a failure, skipped result, or warning.

.Acceptance tests
* AT-QSYS-EXEC-003a — A passing test marked with the quarantine annotation is reported as passed and does not increment the quarantined-failure count.

==== QSYS-EXEC-004 — Quarantine does not mean skipped

A quarantined test MUST execute normally. If it fails, its actual failure status and diagnostic information MUST be retained; quarantine MUST NOT be implemented by skipping or disabling the test.

.Acceptance tests
* AT-QSYS-EXEC-004a — A failing quarantined test is shown as executed and failed, with its exception/message and stack trace available.
* AT-QSYS-EXEC-004b — A separately disabled test remains skipped and is not counted as a quarantined failure.

=== Counts and console output

==== QSYS-REPORT-001 — Separate quarantined-failure count

Every test run MUST expose the number of failed quarantined tests separately from the number of ordinary failures. The quarantined count MUST count test cases, not test classes, worker processes, or suites.

.Acceptance tests
* AT-QSYS-REPORT-001a — A run with three quarantined failing test cases reports a quarantined-failure count of three.
* AT-QSYS-REPORT-001b — A run with passing quarantined tests reports zero quarantined failures.
* AT-QSYS-REPORT-001c — Parallel execution aggregates quarantined failures across workers without double-counting or losing results.

==== QSYS-REPORT-002 — Console summary

The test-run summary MUST contain a distinct, clearly labelled line for quarantined failures, including when the count is zero. Ordinary failures MUST remain distinguishable from quarantined failures.

.Acceptance tests
* AT-QSYS-REPORT-002a — Console output for a run with quarantined failures contains a separate quarantined-failure count.
* AT-QSYS-REPORT-002b — Console output distinguishes ordinary failures from quarantined failures in a mixed run.
* AT-QSYS-REPORT-002c — A run without quarantined failures reports a quarantined-failure count of zero.

==== QSYS-REPORT-003 — Per-test diagnostics

For each quarantined failure, the output MUST identify the fully qualified test name, the failure status, the failure message/exception, and the quarantine reason. The reason MUST be visible without requiring the reader to infer it from a generated property key.

.Acceptance tests
* AT-QSYS-REPORT-003a — Console/log output for a quarantined failure includes its test identity and quarantine reason.
* AT-QSYS-REPORT-003b — Console/log output for a mixed run identifies ordinary failures separately and does not label them as quarantined.

=== JUnit XML

==== QSYS-XML-001 — Preserve test-case identity and outcome

The JUnit XML report MUST contain a test case for every executed test, including quarantined failures. A quarantined failure MUST retain its failure/error diagnostics and MUST be machine-identifiable as quarantined.

.Acceptance tests
* AT-QSYS-XML-001a — XML for a quarantined assertion failure contains the test case, failure details, and quarantine metadata/reason.
* AT-QSYS-XML-001b — XML for a quarantined error contains the test case, error details, and quarantine metadata/reason.
* AT-QSYS-XML-001c — XML for ordinary failures contains no quarantine metadata.

==== QSYS-XML-002 — Report quarantine counts separately

The XML report MUST expose a machine-readable count of quarantined failures separately from ordinary failures, at the report root and/or in a documented properties section. The count MUST represent failed test cases and MUST be consistent with the test-case entries.

.Acceptance tests
* AT-QSYS-XML-002a — XML for a run with both ordinary and quarantined failures exposes distinct counts for each category.
* AT-QSYS-XML-002b — XML counts remain correct when results are grouped into multiple test suites.
* AT-QSYS-XML-002c — XML reports zero quarantined failures when none occurred.

==== QSYS-XML-003 — Escape and preserve reason text

The quarantine reason MUST be preserved as XML-safe text. XML-special characters and non-ASCII characters MUST not corrupt the report.

.Acceptance tests
* AT-QSYS-XML-003a — A reason containing ampersands, angle brackets, quotes, and non-ASCII text round-trips through the generated XML.

=== CI integration

==== QSYS-CI-001 — Quarantined failures do not fail CI

A CI job whose only test failures are quarantined MUST succeed, provided the test process and all other job steps succeed. An ordinary test failure MUST continue to fail CI.

.Acceptance tests
* AT-QSYS-CI-001a — A CI test job with only quarantined failures exits successfully.
* AT-QSYS-CI-001b — A CI test job with an ordinary failure exits unsuccessfully.
* AT-QSYS-CI-001c — A CI test job with both categories exits unsuccessfully because of the ordinary failure.

==== QSYS-CI-002 — CI summary separates quarantine results

The CI report/summary MUST show the quarantined-failure count as a separate line or field, and MUST retain links or annotations for the individual test failures where supported by the reporting integration.

.Acceptance tests
* AT-QSYS-CI-002a — The GitHub Actions job summary shows the quarantined-failure count separately from ordinary failures.
* AT-QSYS-CI-002b — Quarantined failures remain identifiable in the published test report and are not presented as ordinary build-breaking failures.
* AT-QSYS-CI-002c — Ordinary failures continue to be reported as ordinary failures.

== Characterization requirements for existing test behavior

This section records behavior that predates the quarantine feature and must remain
unchanged. These are compatibility requirements, not new quarantine semantics.
The referenced tests characterize the current implementation.

=== CHR-001 — JUnit XML preserves ordinary test outcomes

The JUnit XML report MUST represent successful tests without a failure element,
assertion failures with a `failure` element, runtime errors with an `error`
element, and skipped/ignored/pending tests with a `skipped` element. Failure
messages, exception types, stack traces, test identity, and duration MUST be
preserved when available. Missing failure details MUST produce the existing
fallback diagnostic rather than dropping the test case.

.Characterization tests
* AT-CHR-001a — `TestModuleUtilTests`, tests `success`, `fail`, `fail - empty message`, `error`, and `error - empty message`.
* AT-CHR-001b — `TestModuleUtilTests`, test `skipped`, covers `Skipped`, `Ignored`, and `Pending` statuses.
* AT-CHR-001c — `TestModuleUtilTests`, test `multi test cases`, covers multiple test cases in one suite.

=== CHR-002 — JUnit XML aggregates suite and root counters

The JUnit XML report MUST aggregate the number of tests, failures, errors,
skipped tests, and elapsed time at the report root and per-suite level. A test
case MUST contribute to the counters of exactly one suite and to the root
counters exactly once.

.Characterization tests
* AT-CHR-002a — `TestModuleUtilTests`, test `multi test suites`, covers multiple suites and root aggregation for success/failure.
* AT-CHR-002b — `TestModuleUtilTests`, test `mixed outcomes across test suites`, covers success, failure, error, and skipped outcomes together across two suites.

=== CHR-003 — Ordinary test task failures remain fatal

A test run containing an ordinary failing test MUST be represented as a failed
Mill test task. A run containing only successful tests MUST return successful
test results. A disabled JUnit test MUST remain skipped rather than being
reported as executed or failed.

.Characterization tests
* AT-CHR-003a — `HelloJavaTests`, test group `test`, asserts that the ordinary failing JUnit 4 test task returns `ExecResult.Failure`.
* AT-CHR-003b — `HelloJavaTests`, test group `test`, asserts successful JUnit 4 and JUnit 5 test results.
* AT-CHR-003c — `HelloJavaTests`, test group `test`, asserts that `skippedTest()` has status `Skipped`.

=== CHR-004 — Test subprocess sizing and class-name compaction

The test runner MUST preserve the established subprocess-count behavior for
parallel and non-parallel execution, including empty and single-class inputs.
The console class-name compaction helper MUST produce stable abbreviated names
for sorted class-name inputs.

.Characterization tests
* AT-CHR-004a — `TestModuleUtilTests`, test `testSubprocessCount`.
* AT-CHR-004b — `TestModuleUtilTests`, test `collapseTestClassNames`.

== Acceptance criteria for the quarantine system

The quarantine system is acceptable when:

. Every quarantine declaration has a non-empty reason and uses the common annotation name.
. Quarantined failures are executed, counted, and reported with their original diagnostics.
. Quarantined failures alone do not fail the Mill test task or CI job.
. Ordinary failures continue to fail the Mill test task and CI job.
. Console output, JUnit XML, and CI summaries distinguish quarantined failures from ordinary failures and expose an accurate separate count.
. Every requirement above is covered by its linked passing acceptance tests.
